# dansheng-app contributor instructions

- This is the Flutter App repository, one of two independent product repositories: dansheng-core and dansheng-app. The parent workspace has no Git repository. Do not introduce a monorepo, submodule or subtree as part of workflow setup.
- Read this file and any provided task notes before writing. Use Codex, Claude Code or Herdr's native Git worktree management by default. Work only in the authorized Git-registered worktree; tool-created branch names and native managed detached HEAD are accepted for editing. Create a task branch before authorized commit/push. DS numbering, an extra manager registration and TASK.md are optional. Never edit main or another agent's worktree; reuse a supplied worktree rather than creating a second one.
- Check `git --no-optional-locks status --short --branch`, the absolute Git common directory and worktree registration before work. Ordinary worktrees use real committed bases; DS-001 remains read-only historical preparation. Do not create commits, move refs or merge without the user's approval.
- Apply the four-layer classification in docs/DEVELOPMENT_WORKFLOW.md: generic Core mechanisms, official service connectors/plugins, App platform hosts, and UI. Core service modules own authoritative protocols, business constraints and reusable execution strategies; App owns presentation, user input and platform interaction. UI may prevalidate using Core-provided constraints; Core must validate again at execution. Core owns the authoritative API/ABI and plugin contracts. The current integration is C ABI → JNI/AAR → Kotlin host → Pigeon/Dart; do not add a nonexistent Dart Git package or replace the binding architecture during repository setup.
- Core source and original `C:/Code/dansheng`, `C:/Code/dansheng-app`, DanXi/Dela references and preserved research snapshots are read-only unless a task explicitly grants a different scope. Cross-repository changes link their purpose and exact Core/App revisions, with separately authorized scopes and compatible dependencies; a paired DS ID is optional.
- Use an explicit `-CoreRoot` or `DANSHENG_CORE_ROOT` for a task Core checkout. `DANSHENG_CORE_SDK_DIR` selects the native artifact directory. Otherwise an `app` task tree prefers its paired `core`, then the `dansheng-core` sibling, then an existing legacy `dansheng` sibling. This lookup is not permission to modify another checkout.
- SDK-producing source is selected by CoreRoot. Management/validation tools are selected independently by `-CoreToolsRoot` or `DANSHENG_CORE_TOOLS_ROOT`; automatic lookup only accepts the same Git common directory. Never replace the SDK source to find a validator.
- Automatically prepare the worktree's tools, SDK choice and unique D runtime before builds, through the native tool's setup hook or agent startup. The user need not run New/Initialize/Enter manually; Core's helpers are optional. Keep writable build targets, native SDK output, artifacts, logs and fresh emulator userdata isolated per editing worktree; do not borrow C profiles or signing state for smoke tests.
- Consume an exact `core.lock.json` native-SDK dependency. Development snapshots are labelled as such. Stable builds require a real committed Core revision, verified artifact/resources, pinned Pigeon/Pub dependencies and published acquisition information; never invent a SHA, release or remote CI result.
- Source worktrees do not isolate runtime effects. Use task-scoped Cargo/Pub/Gradle caches, logs, ports, databases, browser profiles and owned emulators. Never copy credentials, user data, signing keys or build outputs into source. Do not attach private profiles to an agent prompt.
- Do not run password login, live reservations/cancellations, submissions, payments, mail sends, signing-key changes, deployments or physical-device operations without concrete authorization. Preserve existing credentials and source files. Unknown external write outcomes require reconciliation before retrying.
- Never reset/clean/force-push, retag a release, overwrite a remote, remove a worktree/branch or rewrite history without explicit approval. Select staged paths carefully; no `git add` is authorized by a request to review or edit files.
- Use Flutter 3.47.7 / Dart 3.13.5 and the existing Pigeon 29.1.1 Pub lock. Relevant local checks: `scripts/check-format.ps1`, `flutter analyze`, `flutter test`, and generation consistency for `pigeons/dansheng.dart`, `lib/bridge.g.dart`, `android/app/src/main/kotlin/org/dansheng/app/Bridge.g.kt`. The format script covers handwritten Dart; Pigeon owns generated binding style. Preserve pubspec.lock.
- Android build/runtime checks require an explicitly prepared native SDK and authorized task resources. Report source/static checks, native compilation, emulator execution, real-service reads and device tests separately; a configuration file or worker summary is not execution evidence.
- After completing each requested change, build a signed Android release APK for the user to review (ARM64 by default), using the verified locked native SDK and task-owned review signing identity. Deliver the actual APK path/link, version, ABI, SHA-256 and observed validation results; a debug APK or test report does not replace this deliverable. Review builds may consume a clearly labelled development snapshot; stable publication still requires the release dependency gates and separate authorization. Preserve prior review artifacts and signing identities. If a build is blocked, report the concrete failure and remaining blocker instead of claiming completion.
- Antigravity workers use project-root cwd and `--add-dir <absolute App worktree> --dangerously-skip-permissions --output-format json --print-timeout 30m --print <prompt>`. Save every conversation_id outside source; resume only its exact ID, verify the returned ID and never continue one conversation concurrently. Different workers have disjoint files and conversations.
- Before handing off: report task/worktree/branch, changed files and Git diff, commands and observed results, Core dependency state, remaining blockers and any pending approvals. Keep docs/workbench-workers.md and previous validation records as historical evidence; do not rewrite them as new test claims.

See [development workflow](docs/DEVELOPMENT_WORKFLOW.md) and [Core compatibility](docs/CORE_COMPATIBILITY.md).
