# dansheng-core contributor instructions

- Implement the approved local-first Rust core plan. Production UI is a separate project.
- Reference work uses the read-only `D:/Code/danxi` and the pinned checkouts under `D:/Code/dansheng-core/reference`; preserve the original `C:/Code/danxi` too. Never copy credentials, user data, or generated build files into this repository.
- Shared core must not depend on Flutter, an embedded browser, MCP, or a school-specific service. Browser execution, credentials, wake-up and notifications are platform ports.
- School endpoints and sports strategies belong to official connectors/plugins. Browser-backed requests must execute in the authenticated page; do not silently substitute Rust HTTP.
- Apply the four-layer classification in docs/DEVELOPMENT_WORKFLOW.md: generic Core mechanisms, official service connectors/plugins, platform hosts, and UI. Official modules own authoritative school protocols, business constraints and reusable execution strategies; hosts execute OS/browser/device capabilities; UI collects input and presents results. UI prevalidation uses service-provided constraints and never replaces Core execution checks. Keep the matching classification rules synchronized in authorized Core/App worktrees.
- No Node.js or Chromium runtime in released core artifacts. JS plugins run through mediated host APIs and explicit grants.
- Treat external write timeouts as uncertain outcomes; reconcile before retrying. Do not execute live reservations, cancellations, mail sends, or other remote mutations without concrete user authorization.
- Never expose secrets in logs, exported diagnostics, fixture data or tests.
- Use meaningful offline fixtures and integration tests. Report cross-compilation, emulator tests, and real-service tests separately.
- Coordinate parallel edits using disjoint file ownership. Do not overwrite another worker's changes or commit unless asked.
- Antigravity workers must use the user's required headless protocol: cwd is the project root; pass `--add-dir <absolute project> --dangerously-skip-permissions --output-format json --print-timeout 30m --print <prompt>`. Persist every returned conversation_id. Continue a worker with its exact `--conversation` ID and verify the returned ID matches. Use separate conversations and disjoint file scopes for parallel workers, never concurrent continuations of the same ID. Main must independently inspect requirements, files, Git diff, builds/tests and out-of-scope edits; summaries alone are not acceptance evidence.

## Repository and agent workflow

- This is the Core member of TWO independent product Git repositories. App is a separate repository. The ordinary parent workspace is never a Git monorepo; do not initialize one, introduce submodules/subtrees, or move existing projects to match an example layout.
- Active primary repositories are `D:/Code/dansheng-core` and `D:/Code/dansheng-app`. The user or Herdr creates and manages worktrees, with `D:/worktree` as the preferred root for new tasks. Agents use the supplied Git worktree and handle implementation, validation, and authorized commits/merges; do not create, relocate, or remove worktrees unless explicitly assigned. Existing `D:/Worktrees` registrations and C-drive project copies remain preserved. Extra task numbering and a workspace manager are optional.
- Keep one long-lived `main`. Agent writes belong to a Git-registered isolated worktree owned by one editing agent. Native tool branch names are accepted; a native managed detached HEAD is accepted for editing, with a task branch created before any authorized commit/push. DS numbers, an extra manager registration and `TASK.md` are optional. Inspect Git common directory, worktree registration, HEAD/status and any provided task notes before writing; a copied directory is not a worktree.
- Original project directories, another agent's worktree, references, credentials and running profiles are read-only. Isolate build targets/caches, SQLite/profile data, temporary files, browser profiles, ports and device data as well as source.
- Never initialize/reinitialize a product repository, clean changes, reset/force checkout, force push, retag, overwrite remotes, delete branches/worktrees or merge/publish without the required user authorization. Preserve dirty, untracked AND ignored files. Worktree/source separation is a workflow guard, not an OS security boundary.
- If a repository has no initial commit, stop normal task provisioning. Do not fake a SHA or silently commit. Product main baselines now exist; DS-001 itself remains an unborn preparation branch awaiting approved attachment/commit, not a normal PR base.
- DS-001 is retained historical preparation. Automatically prepare the assigned worktree's tools, build targets and unique D runtime; the user need not run New/Initialize/Enter manually. Build setup must not provision another worktree. Existing helpers may assist; actual source, SDK artifact and authoritative validator-tools paths are separate choices.
- Core owns C ABI, RPC/plugin API and SDK identity. Use the existing native SDK/JNI/AAR/Pigeon route. Cross-repository changes link their purpose/PRs and exact tested SHAs, integrate compatible Core changes first, and use an App dependency lock. A shared DS ID is optional.
- `tools/workspace` remains an optional paired-task and verification toolbox. If explicitly used, its default is dry-run; mutation requires `-Apply`, and closure requires reviewed `-ConfirmRemoval`. It must not become a mandatory second worktree manager. No automatic remote fetch/push/PR/merge or deletion of runtime data/branches.
- A direct user request to commit or merge authorizes that operation after review and passing checks. Recheck the destination main branch and working tree before integration, preserve other work, and report local merging and remote pushing separately.
- Validate with `git diff --check`, the relevant PowerShell fixture integration tests, and the existing Rust/SDK/platform checks for changed code. Report changed files, worktree/branch/commit, actual diff, tests and limits, dependencies and outstanding approvals after each stage. Never claim remote rules, CI, releases or platform runtime tests have happened without evidence.
- Read [development workflow](docs/DEVELOPMENT_WORKFLOW.md) and [version contract](contracts/VERSIONING.md) before cross-repository work.
